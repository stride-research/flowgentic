# Step 6: `score_with_rosetta` (the real PyRosetta batch function) — success criteria

## What this step is, in plain terms

Step 5's design score is a neural network's opinion of how "plausible" a sequence looks. This
step is the real physics check: thread the designed sequence onto the actual docked structure,
repack the side chains into physically realistic positions, and compute the binding energy
(`dG_separated`) using Rosetta's force field. This is **the only pass/fail gate in the entire
pipeline** — everything upstream only filters or records.

## What changed from the first version of this step

The first version of this step did not call `CageFlow.score_with_rosetta()` at all. It hand-built
inputs from Laura's historical `dock_44` fixture and called `rosetta_scoring.score_sequence()`
directly, in a separate venv (`~/venvs/cageflow`, broken numpy, no pandas), without importing
`CageFlow.py` or using `load_config()`. That made this step inconsistent with every other
step in three independent ways: a different Python environment, no config, and no real chaining
from the earlier stages' output.

All three are fixed now. `~/venvs/cageflow_unified` (see `_shared.py`'s module docstring) gives one
environment with working numpy, pandas, torch, **and** PyRosetta together, so this step runs under
the exact same `module load` + venv as every other step. It uses `load_config()` like steps 1-5.
And it chains `dock_oligomer -> evaluate_geometry -> select_top_docks -> design_interface ->
score_designs -> score_with_rosetta` for real, calling the real top-level batch function —
exactly the same pattern steps 2-5 already use, just extended by one real call.

## A correction, not a bug: the old "real bug" claim was wrong

The first version's `SUCCESS.md` claimed finding a real pipeline bug: that `thread_sequence()`
crashes if handed `mpnn_input.json`'s `{chain: [residues]}` dict instead of a flat list. That
crash was real, but it was a bug in **our own bypass script**, not in CageFlow. Reading
`score_with_rosetta()`'s actual source shows it never reads `design_positions` from
`mpnn_input.json` at all for the one-component path — it computes
`design_positions = flat_interface_resnums(geometries[i])` directly, which already returns a flat
list. The dict/list mismatch only existed because the first version reinvented how
`score_with_rosetta()` sources its inputs instead of calling it. Calling the real function, as
this version does, never hits that shape question in the first place. This is exactly the risk
`_shared.py`'s module docstring warns about: hand-picking inputs instead of calling the real
function risks silently testing a different code path than the one that actually runs.

## What we are checking

- `score_with_rosetta()` returns a dict keyed by exactly the docks that were scored (not a
  superset or subset).
- `per_seq_metrics` has one entry per designed sequence for that dock (dense, matching
  `design_interface`'s own output order — sequences that missed `rosetta_score_cutoff` still get
  an explicit zero-metrics entry, by the real function's own contract).
- At least one sequence per dock actually cleared the cutoff and got real Rosetta scoring (not
  every sequence skipped).
- `dG_separated` (the ddG-style binding energy the real pipeline sorts on) is a real float for
  every entry.
- `group_ddg` is a real float.

## What we are NOT touching

- `score_with_rosetta()` and everything it calls internally (`rosetta_scoring.score_sequence`,
  `thread_sequence`, `apply_symmetric_packing`, `symmdef.write_point_group_symmdef`, dedup
  bookkeeping) — all real, unmodified, called on real data this script generated by chaining the
  real pipeline, not a fixture.

## Why n_docks=1 and num_seq_per_target=1 here, not 2 and 4 like steps 3-5

Steps 3-5 deliberately use `n_docks=2`/`num_seq_per_target=4` to prove "every dock and every
design gets checked, not just the first" — that question is already answered and doesn't need
re-asking at increasing cost. Rosetta scoring is the expensive step (~134s per sequence), so this
step uses `n_docks=1, num_seq_per_target=1`: enough to prove the real function works end to end on
fresh, fully real, freshly chained data, without paying the multi-dock/multi-sequence cost again
for a question already settled upstream. This is a config choice (a probe parameter, same as
steps 3-5's own overrides), not a reconstructed or fabricated input.
